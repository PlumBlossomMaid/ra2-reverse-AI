================================================================================
0x6D20E0  TacticalClass::AdjustForZ（29 callers，63B）
================================================================================
身份实锤：YRpp TacticalClass.h:35
    // convert xyz height to xy height?
    static int __fastcall AdjustForZ(int Height)
        { JMP_STD(0x6D20E0); }
地址 + `static __fastcall`（ecx=Height、无栈参与 ret）+ YRpp 源码注释
「convert xyz height to xy height?」三证吻合。

机器码还原：
    sub esp, 8
    cmp ecx, 0x2d8                  ; ★ Height vs 728
    mov [esp+4], ecx                ; 备份 Height（给 fild 用）
    mov [esp], 0
    jl  over
    mov [esp], 1                    ; ★ Height >= 728 → 加数 = 1
  over:
    fild dword ptr [esp+4]          ; st0 = (double)Height
    fmul qword ptr [0xb0cd48]       ; × 比例常数（★该地址读不出，见 partial）
    fiadd dword ptr [esp]           ; ★ + (Height>=728 ? 1 : 0)
    fadd qword ptr [0x7e1738]       ; ★ + 0.5（实测常量，见下）
    call 0x7c5f00                   ; ★ _ftol（batch 092/093 同族 x87 转换）
    add esp, 8 / ret

常量取证：`read_const.py double 0x7E1738` → **0.5**（raw=3fe0000000000000）。
[0xB0CD48] 报「不在任何节内」= 落在 .bss 虚拟尾巴，文件里没有初值 → 运行时
初始化写入（partial 1）。

语义：`AdjustForZ(Height) = trunc(Height * K + (Height >= 728 ? 1 : 0) + 0.5)`
其中 K = [0xB0CD48] 运行时比例常数。

★原版取整惯癖（照抄，与 QWEN.md 怪癖清单第「阶段 9 造山 §2.5」同款）：
先 `+0.5` 再 `_ftol`，而全局 FPCW=0x0E7F（RC=chop，向零截断，batch 已实锤
WinMain `_control87(_RC_CHOP)`）→ 整体等价于 **round-half-up（正数侧）**，
不是 x87 FRNDINT 的 ties-to-even。对负数侧会退化成 toward-zero 方向的
half-up 变体——本函数 Height 恒非负，故不影响，但复刻必须保留
「+0.5 后 _ftol」这个动作序列而非替换为 std::nearbyint/round。

★`Height >= 728` 的 +1 分支：728 = 0x2D8，是高度上界相关的分段补偿
（超出某阈值时整体结果 +1）。0x2D8 的来历未追（partial 2）。

紧邻第二成员 0x6D2120（16B，反向）：
    push ecx / mov [esp], ecx
    fild dword ptr [esp]
    fsub qword ptr [0x7e1738]       ; ★ -0.5（同一常量）
    fmul qword ptr [0xb0cdd8]       ; × 逆比例常数
    call 0x7c5f00 / pop ecx / ret
语义：`trunc((Height - 0.5) * K2)`——与 0x6D20E0 成对，一加一减对称
「XY→Z / Z→XY」互逆变换的两个方向。两条都走 _ftol 收尾。

的实参形态未逐个回查，不下断言。

================================================================================
★方法论补证：0x4073C0 ↔ 0x4073E0 孪生关系字节级实锤
================================================================================
batch 089 登记 0x4073C0（安全解引用谓词）时，台账写了「0x4073E0 是逐字节相同
孪生（36+31 callers 两处编译副本）」——但当时只有 disasm 目视比对本项目通用
纪律「不做归一化逐字节比对就不写『已证为副本』」。本批补做原始字节 dump：

    0x004073C0 = 85c9740b8b0185c074073b4008750233c0c3
    0x004073E0 = 85c9740b8b0185c074073b4008750233c0c3
                 ↑ 完全一致的 18 字节

逐条对应：85c9(test ecx,ecx) 740b(je +0x0B→本函数内 xor 段) 8b01(mov eax,[ecx])
85c0(test eax,eax) 7407(je +0x07→ret) 3b4008(cmp eax,[eax+8]) 7502(jne +0x02→ret)
33c0(xor eax,eax) c3(ret)。

相对跳转偏移 0x0B/0x07/0x02 全同，绝对落点因基址差 0x20 而异（0x4073CF vs
0x4073EF 等）——**这正是「同一源码在两个 TU 各编译出一份」的机器码指纹**
（同 batch 085 的 c_str()/[] 孪生族、batch 086 的坐标菱形谓词同款现象）。

结论：batch 089 台账该断言由「目视比对」升级为「原始字节 dump 完全一致」，
**无需修正内容，只需记录证据强度提升**。两个地址各自 36/31 个调用点意味着
编译器为不同调用上下文各内联了一份。
