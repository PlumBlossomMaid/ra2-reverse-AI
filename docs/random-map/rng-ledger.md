## 一、先划边界：谁在用生成器那个 Randomizer

生成器有自己的全局 `Randomizer @ 0xABE890`，**整张地图只播种一次**
（`0x598985`，种子取自 `.sed` 的 `Seed=`）。引擎另有一份 Randomizer，
两者状态互不相干。

全 `.text` 搜立即数 `0xABE890`：**153 处引用，全部落在 `0x58B772 – 0x5AC192`**，
区间之外一处也没有。按 `this` 把每处配到后面的 `call`：

| 类别 | 处数 |
|------|------|
| `Randomizer::Random` | **150** |
| `Randomizer::RandomRanged` | **0** |
| 播种（CRT 静态初始化，seed=0，与生成无关） | 1 |
| 非取数（`rep movsd` 拷贝 / 相邻函数尾部巧合） | 2 |

要区间随机时，生成器一律走自己的 `PickRange`（`0x598030`，浮点比例 + 拒绝采样）。

> ⚠️ 只按"调用了哪个函数"统计会把引擎那份 Randomizer 算进来，
> 早前得出的"142 处 / `RandomRanged` 14 处"就是这么错的。**判定必须看 `this`。**

## 二、再筛一遍：其中 46 处是死代码

把 150 处按所在函数分组，往上追引用（`E8/E9` 相对跳转 + 全镜像任意 4 字节绝对值，
后者覆盖虚表项与跳转表项），得到一个意外的结果：

**22 个函数、46 个取数点，在整个 4MB 镜像里没有任何东西指向它们。**

| 函数 | 取数点数 | 入口引用数 |
|------|---------|-----------|
| `0x5A5020` | 1 | 0 ← 一整棵子树的根 |
| ├ `0x5A5360` | 3 | 1（来自 `0x5A5308`，在 `0x5A5020` 体内） |
| ├ `0x5A5B50` | 4 | 1 |
| │ ├ `0x5A6D80` | 2 | 2 |
| │ └ `0x5A7070` | 1 | 2 |
| ├ `0x5A6510` | 3 | 1 |
| ├ `0x5A6920` | 4 | 1 |
| ├ `0x5A78D0` | 2 | 1 |
| ├ `0x5A82E0` | 4 | 2 |
| ├ `0x5A8720` | 5 | 2 |
| └ `0x5A89D0` → `0x5A8F00` | 1 + 4 | 2 |
| `0x5A80B0` | 1 | 0 ← 另一个根，也指向上面那批 |
| `0x58BE20` / `0x58C320` | 2 / 2 | 0 / 0 |
| `0x58C4A0` / `0x58C5A0` | 1 / 1 | 0 / 0 |
| `0x59D480` / `0x5A1190` / `0x5A2ED0` | 1 / 1 / 1 | 全 0 |
| `0x5A4AE0` / `0x5A4FA0` / `0x5A5AE0` | 1 / 1 / 1 | 全 0 |

判死用的是**传递闭包**：入口零引用即死；引用它的又全在已判死的函数体内，也死。
`0x5A5020` 那棵子树（`0x5A5300` 附近连着 6 个 `call`）就是这么整棵被摘掉的。

**这条结论的边界（诚实记录）**：零引用只证明*没有静态引用*。
理论上还能靠地址算术拼出入口，但 MSVC 6 的 C++ 不会生成这种代码，
且这些函数连一处 4 字节绝对值都搜不到，连塞进跳转表都没有。故判定为
链接器保留下来的死代码（多半是 TS 时代遗留、YR 里已不再调用的地形生成分支）。

### 为什么编译器没把它们优化掉

因为**编译器没资格删**，能删的是链接器，而这一版链接器没开那个开关。

1. **编译期：外部链接就必须生成。** 这些是 MapGen 那几个类的非 static 成员函数，
   编译 `MapGen.cpp` 这一个翻译单元时无从知道别的 `.obj` 会不会调，只能照发。
   「死」是**整个程序链接完之后**才成立的全局性质，单 TU 里看不出来。
2. **链接期：MSVC 6 默认不剪。** 要删未引用函数得 `/Gy`（每函数一个 COMDAT）
   + `/OPT:REF` 同时成立。没有 `/Gy` 时一个 `.obj` 的 `.text` 是**一整块**，
   只要里面有任一符号被引用，整块连同旁边没人要的函数一起进 exe。
3. **我们自己的数据反证了这一点**：这 22 个函数**夹在活代码中间**、连续散布在
   `0x58BE20`-`0x5A8F00` 的 MapGen 区里，而不是被聚到一处。若开了 `/Gy + /OPT:REF`，
   全 exe 就不该存在零引用函数。同一个 exe 里还留着 MapGen.cpp 那类调试字符串
   和阶段日志，本来就不是激进优化的构建配置。

反过来说，**正因为链接器没剪，我们才能统计到它们**——这也是上面那套判死方法
能成立的前提。

**于是要还原的是 104 个取数点，不是 150 个。**

取数点落在被访问指令上才算这个阶段用得到。

> 为什么不用 Ghidra 的调用图：MapGen 这段里相当多的函数 Ghidra 根本没定义，

## 四、`UniformUnit` 是通过函数指针调用的

`0x598000` 全镜像只有两处引用，都是**写入**，一次 `call` 都没有：

```
0x58B79D   mov dword ptr [0xABDFC8], 0x598000   ; 全局对象构造
0x5989BF   mov dword ptr [esp+0x2C], 0x598000   ; 每次生成前重填，随后 rep movsd 进 0xABDFB8
```

真正的调用点在 `NormalDeviate`（`0x5980C0`）体内：

```
0x5980DE   call dword ptr [esi + 0x10]     ; esi = 0xABDFB8
0x5980ED   call dword ptr [esi + 0x10]
```

递归下降反汇编跟不出函数指针，所以这条边在 `call_closure.py` 里是**人工补的**
（`INDIRECT = {0x5980C0: [0x598000]}`）。补之前"Creating hills 阶段一个随机数都不取"，
补之后才对上。

`0x598000` 本身极短，就是 `Random() × (1/(2^32-1))`，返回 `[0,1]` 的 double：

```
0x598003   mov ecx, 0xABE890
0x598008   call Randomizer::Random
0x598019   fild qword ptr [esp]              ; 借 64 位 fild 做 uint32 -> double
0x59801D   fmul qword ptr [0x7ED898]         ; = 2.3283064370807974e-10 = 1/(2^32-1)
0x598026   ret
```

### 对账本的影响：这一处的取数个数是「不定 + 跨阶段串」

`NormalDeviate` 的算法本身（Marsaglia 极坐标法、缓存第二个偏差、拒绝采样）
已在 [fast-math.md](fast-math.md) §三还原并逐位对拍，这里只补账本关心的两点：

- **取数个数不定**：命中缓存 **0 个**；未命中则每轮抽 **2 个**，直到 `0 < s < 1`
- **状态跨阶段串**：`0xABDFB8` 那 6 个 dword 只在 `0x5989A2` 处、
  也就是**每张地图开始前**整体重填一次。阶段 8 留下的缓存会被阶段 9 吃掉。
  复刻时这个缓存标志必须与随机数发生器同生命周期，**不能在阶段边界清零**

顺带一个 `fast-math.md` 没记的细节：那 6 个 dword 里 `+0x04` **压根没被初始化**
（`0x5989A2` 拷贝的栈缓冲区只写了 `+0x00` / `+0x08` / `+0x0C` / `+0x10`），
它也从未被读——照抄时留空即可，不要"补"一个初值上去。
