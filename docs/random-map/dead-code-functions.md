# RMG 死代码函数取证（22 个零引用函数）

> 目标：判定 `rng-ledger.md` §二 那 22 个零引用函数"原本属于什么"。
> 前置条件已满足（104 活取数点全还原 + 端到端逐字节闭环）。
> 取证手段：`disasm.py`（capstone 直反汇编）+ callgraph `functions.tsv`/`direct_edges.tsv`
> + `xref_abs.py`/`xref_rel32.py` 双工具独立复核。**不依赖 Ghidra 的函数边界。**

## 结论摘要

1. **「死代码」判定成立**——至少对已复核的 `0x58BE20`：`xref_abs.py` 与 `xref_rel32.py`
   两个独立工具都报 0 处引用，与 `functions.tsv`/`direct_edges.tsv` 的零入边一致。
   即：函数体完整存在，但整个 4MB 镜像里没有任何静态引用。

2. **「疑似整套地形生成方案」这一假设不成立**——已取证的函数是**实体放置**
   （在随机合法格子上放建筑/单位），不是地形整形。依据见下。

3. **它们不是"TS 时代遗物"，而是 YR 自己的 MapGen 层代码**：用的是和活代码
   **完全同一套**全局与惯用法（`Randomizer @0xABE890`、work 数组 `@0xABED10`
   每格 0x50、边长 `@0x89C2DC`、同一套 `scaled_random` 拒绝采样）。
   形态更像**同一时期被放弃的另一套做法**，而非跨时代残留。⚠️ 此为推断，未实证。

## 数据质量问题：11 个函数被 Ghidra 误判为「1 字节函数」

`functions.tsv` 把下列 11 个记为 `body_bytes=1` 且出入边全 0：

`0x58BE20` `0x58C320` `0x58C4A0` `0x58C5A0` `0x59D480` `0x5A1190`
`0x5A2ED0` `0x5A4AE0` `0x5A4FA0` `0x5A5AE0` `0x5A80B0`

**这是错的。** 用「反汇编到第一个 `ret`」实测 11 个函数真实长度，**没有一个是
1 字节**：

| 地址 | 真实长度 | 内部调用特征 |
|---|---|---|
| `0x58BE20` | 126 B | `Random` + `_ftol` |
| `0x58C320` | 142 B | `Random` + `_ftol` |
| `0x58C4A0` | 231 B | + `GetCellAt(0x5657A0)` + `0x486380` |
| `0x58C5A0` | 259 B | + `GetCellAt` + `0x56D230` + `0x486380` |
| `0x59D480` | 137 B | `0x4CAC40` + `Random` |
| `0x5A1190` | 210 B | `0x4CADE0` + `Random` |
| `0x5A2ED0` | 117 B | `0x4CAC40` + `Random` |
| `0x5A4AE0` | 117 B | `0x4CAC40` + `Random`（与上**同构**） |
| `0x5A4FA0` | 117 B | `0x4CAC40` + `Random`（与上**同构**） |
| `0x5A5AE0` | 107 B | 只有 `Random` |
| `0x5A80B0` | 546 B | 12 个 call，第二个零引用根 |

`rng_ledger.txt` 记的取数点（`58BE48`/`58BECB` 等）落在实测函数体内，与反汇编
吻合——**是 functions.tsv 的边界识别错了，不是 ledger 记错**。

⚠️ **形态推测（未实证）**：`0x5A2ED0`/`0x5A4AE0`/`0x5A4FA0` 长度相同、调用特征
相同，疑为**同一辅助函数的三份复制**。短小且高度重复的函数形状，正是 Ghidra
边界识别器容易退化成 1 字节的情形——这与「11 个全被判 1 字节」的现象吻合。

⚠️ 影响面：这批 callgraph 数据后续被 frontier 流程当基准用。凡依赖
`functions.tsv` 的 `body_bytes`/`unique_callers` 做筛选的地方，对这 11 个地址
都可能得出错误结论。**引用计数本身仍可信**（xref 双工具独立复核过），只是
函数体大小不可信。

## 已确认的函数语义

### `0x58BE20` —— 随机取一个「已占用」的格子

```
eax = [0x89C2dc]（边长 side）；eax = side*side；esi = side*side - 1
scale = (double)(side*side)
loop:
  v = _ftol( (double)(uint32)Random() * scale * [0x7ed898] )   // = *total/4294967295.0
  if (v > side*side-1) goto loop;                               // 拒绝采样
  p = [0xabed10] + v*0x50                                       // lea ecx,[eax+eax*4]; shl ecx,4
  if (p->x == 0 && p->y == 0) goto loop;                        // 空格子 → 重抽
  *this = *p;  return;
```

- `side*0x50` 的索引方式与活代码（`0x578E60` 分配 side²×0x50）同一套。
- 返回值 = `work[v]` 首 dword，即 `x | (y<<16)`。
- 同地址 `0x58BEA0` 是同构的第二份（同样 prologue、同样惯用法）。

### `0x5A6510` —— 按派生区间取随机槽位，再除 2 传下去

```
n = arg->[0x10] / 10        // imul 0x66666667; sar edx,2   => >>34
m = arg->[0x10] / 5         // imul 0x66666667; sar edx,3   => >>35
hi = n - m + 1 ; lo = m
loop:  v = _ftol( (double)(uint32)Random() * hi * [0x7ed898] + lo )
       if (v > n) goto loop;
       FUN_005ad6f0( v >> 1, 0, 0, &out )
```

⚠️ `n`/`m` 的关系在正数下 `m > n`（`x/5 > x/10`），区间方向存疑；
需确认 `arg->[0x10]` 的取值域才能定语义。**暂标 partial**。

## 分类（按出边证据，⚠️ 为推断）

`direct_edges.tsv` 出边显示这批函数反复调用：

| 符号 | 出自 | 指向的子系统 |
|---|---|---|
| `BuildingClass::BuildingClass` | `0x5A6510` `0x5A82E0` | 放置建筑对象 |
| `MapClass::IsWithinUsableArea` | `0x5A6510` `0x5A6920` `0x5A82E0` `0x5A8720` | 合法性校验 |
| `0x5657A0`（GetCellAt） | 上述全部 | 坐标↔格子 |
| `UnitClass::AStarAttempt` | `0x5A6920` `0x5A8720` | ⚠️ 寻路 |
| `InfantryClass::GetFireError` | `0x5A6920` `0x5A8720` | ⚠️ 武器开火判定 |
| `operator_new` / `delete` | 多数 | 堆对象 |

**读法**：主线是「随机选合法格子 → 造建筑 → 校验可用区」，即**遭遇战实体布置**，
不是地形整形（后者应出现 tile/level/ramp/rim/trig 等地形写入）。

⚠️ **未解释的矛盾**：`0x5A6920`/`0x5A8720` 调用 `GetFireError`（开火判定）与
`AStarAttempt`（寻路）是**玩法函数**，地图生成不该碰。

**2026-10-13 修正**：查 `functions.tsv` 的 `symbol_source` 字段，上述
`GetFireError` / `AStarAttempt` / `BuildingClass::BuildingClass` /
`MapClass::IsWithinUsableArea` 全部标记为 **`USER_DEFINED`**——即符号名来自
**YRpp 开源符号覆盖**，而非从本 exe 实锤。所以"出现玩法函数"这一矛盾
**可能只是命名出处问题**，不能当作 TU 归属的铁证。本文档中所有带类名的调用
一律视为「推断名」，实锤的只是**地址**（地址来自 `direct_edges.tsv`，
是本 exe 内的真实 call 边）。**待查**：用汇编实锤被调函数到底是不是寻路/开火。

## 死代码真实规模：远大于那 22 个

`rng-ledger` §二 那 22 个是「**有取数点且零引用**」的子集，不含无取数点的
零调用函数。按 `functions.tsv` 的 `unique_callers==0` 全表统计：

| 指标 | 数值 |
|---|---|
| 零调用函数 | **2706 个 / 8655（31.3%）** |
| 零调用函数总字节 | 541927（占 `function_bytes` 的 **20.8%**） |

散布区间内的零调用**根**（其余树内函数因有内部调用者而不在此列）：

- `0x58BE20-0x59A63A` 前段 4 个：`0x58BE20` `0x58C320` `0x58C4A0` `0x58C5A0`
- `0x59A63B-0x5A8F00` 后段 11 个：`0x59D480` `0x5A1190` `0x5A1E10` `0x5A2ED0`
  `0x5A3A60` `0x5A4AE0` `0x5A4FA0` `0x5A5020` `0x5A5AE0` `0x5A6BA0` `0x5A80B0`

⚠️ 其中 `0x5A1E10`(56B) `0x5A3A60`(125B) `0x5A6BA0`(110B) **不在原 22 个
清单里**——它们零调用但无 RNG 取数点，原筛选口径（按取数点分组）漏掉了。
`0x5A1E10` 与 `0x5A3A60` 已用 `xref_abs.py` + `xref_rel32.py` 双工具复核，
各报 0 处引用，确认同属零引用死代码。

## TU 归属铁证：MapGen.cpp 自身含零调用函数

`0x597380` 同时满足两个独立证明：

1. **归属 MapGen.cpp**：函数体内 `0x5973EC` 处为调试宏
   `push 0xF5E`（行号 3934）+ `push 0x82BA48`（MapGen.cpp 源文件字符串 VA，
   与 `scan_source_macros` 报告的 `str@0x82ba48` 一致）。
2. **零引用**：`xref_abs.py` 与 `xref_rel32.py` **各报 0 处**。

且 MapGen.cpp 断言区间（20307 字节）内共有 **5 个**零调用函数：
`0x595740`(404B) `0x5958E0`(725B) `0x596300`(2385B) `0x597380`(172B) `0x598000`(39B)。

> **结论：「MapGen.cpp 自身含有零调用函数」是已证事实，不再是推断。**

这使"死代码零散分布"这一现象获得解释：链接器未开 `/OPT:REF`，同一个 TU
内部就会有从未被调用的成员函数。

`scan_source_macros.py` 实测 36 个 TU，`MapGen.cpp` 的断言宏只覆盖
**`0x5956E7-0x59A63A`**（21 处，行 3934-6746）。而这 22 个函数散布在
**`0x58BE20-0x5A8F00`**，明显溢出该区间。断言宏只出现在有 `assert` 的代码处，
所以「落在宏区间外」**不能**推出「不是 MapGen.cpp」。

**2026-10-13 取证**——子树根 `0x5A5020` 的反汇编调用序列里有：

```
005a50c0  call 0x598030     ← 活函数（10 个外部调用者）
005a52d4  call 0x5980c0     ← 活函数（11 个外部调用者）
```

两个都在 MapGen.cpp 断言区间 `0x5956E7-0x59A63A` 内。加上死代码与活代码共用
同一套全局（`Randomizer @0xABE890`、work 数组 `@0xABED10`、边长 `@0x89C2DC`）
和同一套 `scaled_random` 惯用法，且物理相邻——**强证据指向同属 MapGen.cpp
（YR 自己的代码层），而非 TS 时代跨时代残留**。

**断言行号分布解释了区间外溢**（`scan_source_macros.py MapGen` 明细）：
MapGen.cpp 的 21 处断言行号为 3934（5 处，分别在 `0x5956E7`/`0x595713`/
`0x596620`/`0x596802`/`0x5973EC`）、4883–4949、5433、5572–5590、6746，
行号跨度大且分布稀疏。这说明断言只落在**源文件中后段**——3934 行之前与
6746 行之后的代码都不带断言。因此死代码落在宏区间之外（`0x58BE20-0x5A8F00`
横跨 `MapGen.cpp` 断言区的前后两侧）**与「同属 MapGen.cpp」并不矛盾**，
它们很可能就是该 TU 里无断言的那部分代码。

⚠️ **仍是推断而非铁证**：调用关系 + 全局共用 + 物理相邻 + 断言行号分布
都不能单独证明 TU 归属。要钉死需：① 对 `0x598030`/`0x5980C0` 实锤其确在
MapGen.cpp；② 或找该 exe 的 `.obj`/COMDAT 边界证据。**未做**。

## 两个零引用根：编排树结构

`0x5A5020`（827 B）与 `0x5A80B0`（546 B）是两个零引用根，二者都直接触碰
MapGen/RMG 的三样核心设施：

| 设施 | 用途 | `0x5A5020` | `0x5A80B0` |
|---|---|---|---|
| `[0x89C2DC]` | 工作数组边长 | 读 | 读 3 次 |
| `[0xABED10]` | 每格 0x50 字节工作记录 | 索引 | mov + 读 |
| `Randomizer @0xABE890` | 引擎随机源 | 调 | mov + 调 |

`0x5A80B0` 另调用 `0x5A7250` 与 `MapClass::IsWithinUsableArea`(0x578460)，
并在函数尾部**按固定顺序**再调用另外三个死代码子树根：
`0x5A89D0` → `0x5A82E0` → `0x5A8720`。

`0x5A5020` 的尾部同样以固定顺序调用 `0x5A5360` → `0x5A5B50` → `0x5A6510`
→ `0x5A6920` → `0x5A78D0`。

> **这批函数彼此按固定顺序互相调用、形成一棵有序的编排树**——它们不是零散
> 残留，而是**一整套设计完成但从未被接线的算法**。结合它们与活代码共用同一
> 套全局与惯用法，读法是：YR 自己在 MapGen.cpp 里实现了一套完整的
> 「遭遇战实体布置」方案，最终决定启用的是另一套（那 104 个活取数点所属的
> 方案），这套就被链接器留了下来。

⚠️ 「最终启用了另一套」这一读法是**推断**：本 exe 内没有留下「哪套被启用」
的直接痕迹，零引用只能证明静态不可达。

### `0x5A6BA0` —— 锚点邻域格子合法性扫描器（零取数点）

```
X = *(int16*)(ecx);  Y = *(int16*)(ecx+2)
for y in [Y-7, Y+7):            ; 外层
  for x in [X-7, X+7):          ; 内层
    if (FUN_004863d0( GetCellAt(MapClass::Instance@0x87F7E8, x, y) ))
        return false;           ; al=0  —— 邻域内有可用格
return true;                    ; al=1  —— 邻域全不可用
```

**不调用 `Randomizer`、零取数点**（实测 110 字节，仅 2 个 call：`GetCellAt`
与 `FUN_004863D0`）。

因此它不是布置逻辑本身，而是布置逻辑要用的**探测/校验工具**：在给定锚点
附近（±7 格）找一块可用地。

这解释了两件事：① 它零调用但落在死代码区——工具函数随主算法一起被废弃；
② 它**被原 22 个清单漏掉**——`rng-ledger` §二 按「取数点分组」筛选，
不消耗随机数的辅助函数根本不会进入清单。这是原筛选口径的系统性盲区，
不止影响 `0x5A6BA0`/`0x5A1E10`/`0x5A3A60` 三个。

### `0x5A1E10` —— MapType 3/4 门禁（与活代码平行的一套编排）

```
if (this->[0x3c] == 3 || this->[0x3c] == 4) {
    FUN_0058ebc0(this);
    FUN_0058ef10(this);
    FUN_005a19e0(this);
    RepaintAll(MapClass::Instance, /*owner=*/0, /*?=*/-1);   // 0x578E60
    FUN_005a17f0(this);
}
```

实测 56 字节，**零取数点**。

关键：`0x578E60` 带 `(-1, 0)` 实参——这正是
[stage-making-regions.md](stage-making-regions.md) 记录的 `RepaintAll` 实锤
调用形态（调用点 `0x598D73` 为 `push -1`）。故这是一条 **MapType 3/4 门禁**。

> **这是本轮最重要的发现**：死代码区里躺着一份**与活代码 MapType 3/4 分支
> 平行的一套编排**。它直接回答了「它们被什么替代了」——不是被另一套地形
> 方案替代，而是被**另一套 MapType 3/4 编排**替代。原版作者为同一分支写过
> 两版，最终保留一版、链接器把另一版留下。

⚠️ 「保留了一版」是**推断**：零引用只证明静态不可达，exe 内没有痕迹表明
哪一版曾被调用。

### `0x5A3A60` —— 全图扫描 + `Y*side+X` 线性索引（零取数点）

```
MapClass::CellIterator_Reset(0x578350)
loop {
    cell = MapClass::CellIterator_Next(0x578290);
    work = [0xabed10] + index * side;      // imul eax, [0x89c2dc]
    ...
}
MapClass::CellIterator_Next(0x578290)     // 第二轮遍历
```

实测 125 字节，零取数点。`imul eax, [0x89C2dc]`（× 边长）即 RMG 工作数组
的 `Y*side + X` 线性索引约定——与活代码同一套寻址。

### `0x5A5AE0` —— 切比雪夫距离 + 随机抖动（放置偏移取点）

```
dx = p1.x - p2.x ; dy = p1.y - p2.y      ; 两侧都是 movsx int16
adx = abs(dx) ; ady = abs(dy)            ; cdq/xor/sub 无分支绝对值惯用法
base = max(adx, ady)                     ; 切比雪夫距离，非欧氏
jitter = (double)(uint32)Random() * [0x7ED818] * [0x7ED898]
return base + jitter;
```

实测 107 字节，**1 个取数点**（`Randomizer::Random`）。

要点：
- 两个入参按 `movsx word ptr` 读——是**格子坐标对**（各 2 个 int16），
  不是对象指针；
- 取 `max(|dx|,|dy|)` 而非 `sqrt(dx²+dy²)`——切比雪夫距离是**格子世界**
  的自然度量；
- `[0x7ED818]` 与 `[0x7ED898]` 两个常量连乘，与活代码的 `scaled_random`
  惯用法同款（后者是 `1/4294967295.0`）。

这是放置实体时"在两个锚点之间取一个偏移格"的写法，与 `0x5A6BA0`
（邻域合法性扫描）配套：先按切比雪夫距离取偏移，再用扫描器验证落点。

### `0x5A5360` —— 废弃方案里最大的单个函数（1913 B）

```
operator_new ×3                       // 开场三次堆分配
MapClass::CellIterator_Reset(0x578350)
MapClass::CellIterator_Next(0x578290)  ×N
  imul eax, [0x89c2dc]                 // × 边长 → Y*side+X 线性索引
  work = [0xabed10]
FUN_005ad870(...) ; operator_new ; FUN_0042fcb0(...)   // 造对象
GetCellAt(0x5657a0) ; FUN_00486380
Randomizer::Random ×3                 // 3 个取数点
FUN_007c8b3d (delete) ×3
```

实测 1913 字节，3 个取数点。与 `0x5A3A60` 相比：同一套「CellIterator 双轮
遍历 + `imul [0x89C2DC]` 线性索引」骨架，多了三次堆分配与对象构造。

> 至此这套废弃方案的形状已经清楚：**遍历 work 数组 → 校验格子 → 造对象 →
> 写回**，全程不碰 tile/level/ramp 等地形字段。与 `0x58BE20`（挑已占用格）、
> `0x5A6BA0`（邻域扫描）、`0x5A5AE0`（切比雪夫距离取偏移）、
> `0x5A6510`（派生区间取槽位）拼起来是一套完整的「遭遇战实体布置」。

### `0x5A5B50` —— 废弃方案里第二个大函数（2482 B）

调用骨架（去掉 4 个取数点调用后）：

```
FUN_005a7640                                  ; 开场
FUN_005a6d80 ×2      (死代码集内)
FUN_005a7070 ×2      (死代码集内)
FUN_005a6c10 ×15     ← 高频
FUN_005a7250 ×7      ← 高频
FUN_005a76e0 ×2
GetCellAt(0x5657a0) ; FUN_00486730 ×3 ; CellClass::GetNeighbourCell(0x481810)
```

`0x5A6C10` 与 `0x5A7250` 交替出现、合计 22 次，是 **MSVC 把小循环展开**
的典型形态——每轮「查一次 `0x5A6C10`、查一次 `0x5A7250`」。

> **两个筛选盲区（都系统性、都不止影响个别函数）**：
> ① **零取数**的辅助函数被 `rng-ledger` §二「按取数点分组」口径漏掉
>    （`0x5A6BA0`/`0x5A1E10`/`0x5A3A60` …）；
> ② **被死代码内部调用**的辅助函数，其 `unique_callers` 不为 0，因而不在
>    「零调用函数」口径内——但它们同样是这套废弃方案的组成部分。
>    `0x5A6C10`/`0x5A7250` 就是这一类：被调 15 次/7 次，却既不在原 22 个
>    清单、也不在零调用统计里。

### `0x5A6C10` —— 表派发 + 虚调用 + 坐标累加（被调 15 次）

```
obj = [0xA8ED2C][ecx];                 // 全局对象表，按第 1 参索引
if (obj->vtable[0x27]() == 0) return;  // 虚调用（vtable 槽 0x27）
n1 = obj->[0x2E8];  n2 = obj->[0x2E4]; // 两个计数域
for (i = 0; i < n2; i++)
  for (j = 0; j < n1; j++) {
    acc_x += (int16)*edx;  acc_y += (int16)*(edx+2);   // 16 位累加
    if (acc_x + acc_y > [0xABED04]) → 越界分支
  }
```

⚠️ **部分未确认**：`[0xA8ED2C]` 那张表装的是什么对象、`vtable+0x27`
是哪个虚函数、`[0xABED04]` 具体含义——三者都还需进一步取证。
已实锤的只是：经全局表按参数索引取对象、调 vtable 槽 0x27、随后按两个
计数域做嵌套循环 16 位坐标累加并与 `[0xABED04]` 比界。

### `0x5A7250` —— 坐标组合的边界校验（被调 7 次）

读入参结构 `{int16 a; int16 b; int32 c}`，把下列组合逐一与全局
`[0xABED04]`（下界侧）和 `[0xABED08]`（上界侧）比界，任一越界即走 0x5A742A
的失败出口：

```
a + b
a - b
b - a
(a + c - 1) + b
```

⚠️ 两点值得注意：① 四个组合都是**两个坐标的加减**（外加 `c` 参与的第三项），
这是「矩形/区间合法性」的标准写法；② `[0xABED04]` 与 `[0xABED08]` 与 work
数组基址 `[0xABED10]` **地址相邻**（相差 4 和 8），极可能是同一结构里的两个
尺寸字段或紧邻的两个维度全局——**待查**。

## 孪生签名分析：排除「活函数的未引用复制品」

按「出边目标集合」作签名，在全表 8655 个函数里检索同签名者：

| 结果 | 数量 |
|---|---|
| 有出边且签名全表唯一 | 11 |
| 同签名但成对（`0x5A6920` ↔ `0x5A8720`） | 2 |
| 无出边（Ghidra 边界误判，见上） | 11 |

**没有任何一个死代码函数在活代码里找到同签名孪生**。这排除了「死代码是某个
活函数的未引用复制品」这一假设——它们是**独一份、从没被接线**的算法。
